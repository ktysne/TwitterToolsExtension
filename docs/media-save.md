# 画像と動画の保存

## やりたいこと

画像を含む投稿の画像を、ボタン一発で原寸保存する(1 枚でも複数枚でも対象)。
動画を含む投稿は、その動画も保存対象にする。

## 画像のURL

投稿内の画像は次の形で並ぶ(実DOMで確認)。

```
article 内の  a[href*="/photo/"] > ... > img[src*="pbs.twimg.com/media/<ID>"]
```

表示中の `src` は縮小版で、`name` パラメータが `small` や `360x360` になっている。
これを `name=orig` に変えると原寸が得られる。

```
https://pbs.twimg.com/media/<ID>?format=<fmt>&name=orig
```

`format` は表示中のURLの値(`jpg` や `png` など既知の形式)をそのまま使う。
1 投稿の画像は X の仕様上おおむね最大 4 枚で、コードは枚数を固定せず `a[href*="/photo/"]` を全て列挙する。

## 動画のURL

動画は DOM の `<video>` が blob(MSE)になっていることが多く、URLを取り出せない。
そこで、`interceptor.js` がレスポンスから動画URLを集めておく。

各投稿のメディアは次の場所に入る。

```
tweet.legacy.extended_entities.media[]
  type: "video" | "animated_gif"
  video_info.variants[]  = { content_type, bitrate, url }
  media_url_https        = サムネイル画像（本拡張では未使用）
```

`content_type` が `video/mp4` のものから、`bitrate` が最大のものを選ぶ。
1 投稿に複数の動画/GIF があるため、`tweetId → mp4URL の配列` の形で `<div id="__tteVideoMap">` に JSON で書き出す。

動画URLの収集は、ブロック/ミュート除外フィルタのオン/オフに関係なく常に行う。
フィルタを切っていても動画を保存できるようにするためである。

### 引用ツイートの動画

引用ツイート(`quoted_status_result.result`)の動画は、引用元ツイートの ID で登録される。
一方、引用された動画プレイヤーは外側(引用した側)の `article` 内に描画され、保存ボタンは
`article` 先頭の `a[href*="/status/"]`(＝外側ツイートの ID)で動画を引く。
このままだと ID が一致せず「取得待ち」のまま保存できないため、引用ツイートの動画は
**外側ツイートの ID にも紐づけて**おく(引用元 ID への登録も残すので、引用元を単独表示しても引ける)。
この収集ロジックは `interceptor.js` の `collectTweetVideos()` にまとまっている(DOM 非依存・単体テスト済み)。

## ボタンの設置と保存

`imagesave.js` が、投稿(`article`)を監視してボタンを重ねる。

ボタンの文言は、その投稿で保存される件数を表す（先頭に `⬇` が付く）。

- 動画/GIF を含む投稿：動画が複数なら「⬇ 動画N本を保存」、1 本なら「⬇ 動画を保存」。`__tteVideoMap` からその投稿の全 mp4 URL を引く。
- 画像のみの投稿：1 枚なら「⬇ 画像を保存」、複数枚なら「⬇ 全N枚保存」。各画像を `name=orig` にして集める。
- 画像と動画が混在する投稿：「⬇ メディアN件を保存」。動画と画像を合わせて一括で保存する。

動画URLはレスポンス受信後に確定するため、件数が分かるまでは総称ラベル（「⬇ 動画を保存」「⬇ メディアを保存」）を出し、確定後にラベルを更新する。

ボタンを押すと、`imagesave.js` はファイル名の材料となるメタデータだけを `background.js` へ渡す。
メッセージは次の形式である。

```
{
  type: "tte-download-images",
  items: [{ url, screenName, postId }]
}
```

`background.js` が設定を読み出し、メタデータから保存先とファイル名を組み立てて検証し、`chrome.downloads.download` で順に保存する。
コンテンツスクリプトは `chrome.downloads` を直接呼べないため、service worker が実行役になる。

## 保存先と保存名

設定は `chrome.storage.local` に保存する。

| キー | 既定値 | 内容 |
| --- | --- | --- |
| `saveDir` | `TwitterMedia` | ブラウザのダウンロードフォルダからの相対パス。空欄は既定値として扱う |
| `filenameFormat` | `{screen_name}_{post_id}_{file_name}` | ファイル名の形式。空欄は既定値として扱う |

`filenameFormat` では次の5つのトークンを使える。

- `{screen_name}`：@id
- `{yyyyMMdd}`：投稿日の年月日
- `{HHmmss}`：投稿時刻
- `{post_id}`：投稿ID
- `{file_name}`：元のファイル名（拡張子を除く）。必須

日時は保存時刻ではなく投稿日時である。
投稿ID（Snowflake）から日時を算出し、ブラウザのローカルタイムで整形する。
保存時刻を使うと保存するたびにファイル名が変わり、「同名ファイルは保存しない」の判定が効かなくなるためである。

`{file_name}` と拡張子は、メディアの URL から次のように取り出す。

- 画像：`https://pbs.twimg.com/media/<ID>?format=<fmt>` の `<ID>` と、拡張子 `<fmt>`
- 動画：URL のパスの末尾にある `<名前>.mp4` の `<名前>` と、拡張子 `mp4`

`{file_name}` はメディアごとに異なるので、`filenameFormat` に必須とする。
必須にしておけば、1 投稿に複数のメディアがあっても名前が重ならず、連番を付ける必要が無い。
置く位置は利用者に任せる。
拡張子は形式を展開した後ろに自動で付ける。`{file_name}` をどこに置いても、ファイルの種類が保たれるようにするためである。

既定値での出力は `TwitterMedia/<アカウント>_<投稿ID>_<元のファイル名>.<拡張子>` になる（例：`TwitterMedia/username_1834567890123456789_GXyZ1aBcDeFgHiJ.jpg`）。
投稿IDが取れないときは、`{post_id}` と日時の項目を空文字として展開する。

アカウントと投稿IDは、投稿内の `a[href*="/status/"]` のパスから取り出す。

設定値は入力されたまま保存する。
ポップアップで不正な値を入力したまま閉じても、入力が失われないようにするためである。
ポップアップの保存例と `background.js` は、使う直前に設定値を検証し、不正な値の項目だけを既定値へフォールバックする。

検証の規則は、`chrome.downloads.download` が受け付けるパスの規則（Chrome の `net::IsSafePortablePathComponent`）のうち、実害のあるものを写している。
Chrome が受け付けないパスを渡すとダウンロードの開始が失敗し、利用者から見て保存されないためである。

`saveDir` はブラウザのダウンロードフォルダからの相対パスでなければならない。
`\` は `/` と同じ区切りとして扱い、連続する `/` と末尾の `/` は無視する。
次のものはフォルダ名に使えない。

- 先頭の `/` やドライブ名を含む絶対パス
- `.` と `..`
- 禁止文字（`" * : < > ? |` など）と、制御文字・書式文字
- 先頭と末尾の空白・`.`・`~`
- `~` を含む 12 文字以下の名前
- Windows の予約名（`con`、`com1`、`conin$` など）
- `.lnk`、`.local`、`.scf`、`.url` で終わる名前

`~` を含む 12 文字以下の名前を使えなくしているのは、Windows で短い名前（8.3 形式）と紛らわしい名前を Chrome が拒否するためである。
Chrome はドットの位置なども見て判定するが、ここでは長さだけで判定して単純にしている。

長さは 100 文字までである。

`filenameFormat` は、禁止文字（`/` を含む）と制御文字・書式文字、先頭の `.`・`~` を使えない。
長さは 100 文字までである。
`{file_name}` を含まない形式も不正として扱う。

展開した結果が Chrome の受け付けないファイル名（150 文字を超える、先頭が空白になるなど）になった場合は、既定の形式で組み立て直す。
既定の形式でも受け付けられない場合は、そのメディアを保存せず、件数にも数えない。

メッセージの値は DOM から取り出したものなので、`background.js` はそのまま信用せずに正規化する。
元のファイル名は、メッセージの値ではなく検証済みの URL から取り出す。
名前の部分は英数字・`_`・`-` だけを許し、拡張子は画像なら `jpg` `jpeg` `png` `webp` `gif`、動画なら `mp4` だけを許す。
元のファイル名を取り出せない項目は保存しない。
アカウントは英数字と `_` 以外を `_` に置き換え、投稿IDは数字だけを受け付ける。

ファイル名の組み立て、保存先パスの検証、パス解決は副作用のない共有モジュール `savepath.js` に分離している。
`background.js` は service worker で `importScripts` により読み込み、`popup.html` は `<script>` タグで読み込む。
Node のテストからは `require` して使う。
content script の `imagesave.js` はこのモジュールを使わず、メタデータだけを送る。

`background.js` の応答は次の形式である。

```
{ ok: true, started, skipped, failed }
```

`started` は開始できたダウンロードの件数、`skipped` は同名ファイルとしてスキップした件数、`failed` は開始に失敗した件数（`download()` の同期の例外と、返された Promise の拒否）である。
開始の失敗を `started` に数えると、パスを Chrome に拒否されたときもボタンに「✓ N件」と出て、保存されていないことに気づけない。
そのため全件の開始結果を待ってから応答する。
`download()` の Promise はダウンロードの開始時点で解決するので、応答はほとんど遅れない。

ボタンの結果表示は次のとおりである。

- 開始できたものがある：「✓ N件」。スキップや失敗があれば「✓ 2件(1件済・1件失敗)」のように括弧で内訳を付ける。
- 開始できたものが無く、失敗がある：「保存失敗」。スキップもあれば「保存失敗(1件済)」。
- 開始できたものも失敗も無く、スキップだけがある：「✓ 保存済み」。

## 同名ファイルのスキップ

設定 `skipExisting`（`chrome.storage.local`、既定 `true`）がオンのとき、保存先に同名のファイルがある項目はダウンロードを発行しない。

`chrome.downloads.download` の `conflictAction` には「スキップ」にあたる値が無い。
そこで `chrome.downloads.search` でダウンロード履歴を引き、同名の記録が「ダウンロード中（`state: "in_progress"`）」または「完了済み（`state: "complete"`）でファイルが実在する（`exists` が `true`）」なら保存済みと見なす。
検索クエリ側では `state` や `exists` で絞らず、結果を見て判定する。
件数も指定せず Chrome の既定（最大 1000 件）に任せる。上限を指定すると、新しい順の上位がすべて中断・削除済みで、それより古い記録に完了済みのものがある場合を見落とすためで、同じ絶対パスの記録が 1000 件を超えることは実際には起きない。
完了済みでも `exists` が `true` でないものを保存済みと見なさないのは、ファイルが無いのに保存されない（利用者から見て黙って失敗する）ことを避けるためである。
逆に見なさなかった場合にできるのは重複ファイルだけで、こちらのほうが害が小さい。
ダウンロード中も対象にするのは、動画のように時間のかかるダウンロードで、完了前に保存ボタンを再度押したときの重複保存を防ぐためである。
`filenameRegex` は絶対パス全体に対する部分一致なので、`[\\/]<保存先>[\\/]<ファイル名>$` の形で末尾一致を見る（区切りは Windows の `\` と他OSの `/` の両方を許す）。

`download()` を呼んだ直後に、そのファイル名をメモリ上の予約（`pending`）に入れる。
存在確認は非同期なので、その待ち時間や、ダウンロードが履歴に載るまでの間に同じファイル名が二重に発行され得る。
これを防ぐため、予約は存在確認の前と `download()` の直前の 2 回確認する。
発行に失敗した場合は予約を外し、再試行がスキップされないようにする。
予約はファイル名とトークンの組で持つ。同じファイル名で二度予約が起きたとき（設定がオフで同名を続けて発行した場合など）に、古い予約の解除や TTL が新しい予約まで消してしまわないようにするためである。
予約は 60 秒で外れる（service worker が再起動すると消えるが、その場合は履歴による判定に戻るだけである）。

設定がオフのときは、Chrome の既定動作（`uniquify`）で `名前 (1).jpg` のように別名保存される。予約による判定も行わない。

制約は次のとおり。

- 判定はブラウザのダウンロード履歴に基づく。履歴を消した場合や、ダウンロード以外の手段（他のアプリでの保存やファイルの移動）で保存先に置かれたファイルは検出できない。
- 逆に、保存元はこの拡張機能に限定していない。ブラウザや他の拡張機能でダウンロードした履歴にも一致する。同名ファイルがあれば保存しないという設定の趣旨に沿った挙動である。
- `filenameRegex` は絶対パスの末尾一致のため、Chrome のダウンロード先フォルダ自体を変更した場合、変更前のフォルダに保存した履歴にも一致する。現在の保存先には無いファイルをスキップすることがある。拡張機能から現在のダウンロードフォルダの絶対パスを得る手段が無いため、この判定にとどめている。
- 保存先やファイル名の形式を変更すると、変更前の設定で保存したファイルとは名前が一致しないため、同名として検出されない。
- `exists` の情報はブラウザが常時監視しているわけではないため、ファイルを消した直後は古い値が返り、保存されずにスキップされることがある。

## 既知の制約

動画URLは、その投稿を含むレスポンスを `interceptor.js` が見た後に引ける。
投稿は普通そのレスポンスから描画されるため、ボタンを押す時点では引けていることが多い。
URLが未取得のままボタンを押すと、一時的に「取得待ち」と表示して何もしない。
少しスクロールして対象の投稿を読み込み直すと引けるようになる。

動画URLのマップは直近およそ 400 件を保持し、超過分は古いものから破棄する。
長時間スクロールした後は、古い投稿の動画URLが落ちて「取得待ち」に戻ることがある。
